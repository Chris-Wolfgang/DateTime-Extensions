# Migrating from 1.3.2 to 2.0.0

`Wolfgang.Extensions.DateTime` 2.0.0 contains breaking changes. All of them are in `FirstOfWeek`
and `EndOfWeek`, all of them are **behavioural** — every signature is unchanged, so nothing here
shows up at build time — and all of them are confined to the first six days of year 1, the last
seven days of year 9999, or an argument that was never a valid `DayOfWeek`.

**If your dates are in the range real applications use, nothing in this release affects you.**
Upgrade and read no further.

## At a glance

| What changed | Old | New | Action |
|---|---|---|---|
| Week end near `DateTime.MinValue` | `new DateTime(1, 1, 3).EndOfWeek(DayOfWeek.Saturday)` returned `0001-01-07` | returns `0001-01-05` — the correct week end | none; the old answer was wrong by up to 6 days |
| Unrepresentable week start | `FirstOfWeek` returned `DateTime.MinValue` | throws `OverflowException` | catch it, or keep dates out of `0001-01-01`–`0001-01-06` |
| Unrepresentable week end | `EndOfWeek` returned `DateTime.MaxValue` | throws `OverflowException` | catch it, or keep dates out of `9999-12-25`–`9999-12-31` |
| Undefined `DayOfWeek` | returned `0001-01-01` after ~740,000 loop iterations | throws `ArgumentOutOfRangeException` | pass one of the seven values |

## Breaking-change inventory

### `EndOfWeek` returns the correct week end near `DateTime.MinValue`

**What changed.** For 21 `(date, firstDayOfWeek)` pairs in `0001-01-01`–`0001-01-06`, `EndOfWeek`
returned a date in the *following* week — up to six days late.

**Why.** `EndOfWeek` was implemented as `FirstOfWeek(...) + 7 days - 1 tick`. Near `MinValue` a
week's **start** can be unrepresentable while its **end** is perfectly representable, so
`EndOfWeek` inherited a clamp it had no need for and measured seven days from the wrong place. The
two methods are now independent implementations: `FirstOfWeek` counts backwards from the instant,
`EndOfWeek` counts forwards, and neither consults the other.

**Before**

```csharp
// The Saturday-aligned week containing 0001-01-03 runs 0000-12-30 .. 0001-01-05.
System.DateTime moment = new System.DateTime(1, 1, 3, 6, 0, 0);
var result = moment.EndOfWeek(System.DayOfWeek.Saturday);
// 0001-01-07 23:59:59.9999999 - two days into the NEXT Saturday week
```

**After**

```csharp
System.DateTime moment = new System.DateTime(1, 1, 3, 6, 0, 0);
var result = moment.EndOfWeek(System.DayOfWeek.Saturday);
// 0001-01-05 23:59:59.9999999 - the last tick of the week that contains the input
```

> `System.DateTime` is written out in full because this library's own namespace is
> `Wolfgang.Extensions.DateTime`, so the bare name binds to the namespace — see
> [ADR-0002](../adr/0002-namespace-shadows-system-datetime.md). A consumer writing outside that
> namespace can write `DateTime` and `DayOfWeek`.

**Not affected.** Any date from `0001-01-07` onwards. There is no code path by which a date later
than that produced the old answer.

### An unrepresentable week boundary throws `OverflowException`

**What changed.** Where a week boundary falls outside `DateTime`'s range, the methods used to
return `MinValue` or `MaxValue`. They now throw `OverflowException`.

- `FirstOfWeek` throws for 21 pairs in `0001-01-01`–`0001-01-06`.
- `EndOfWeek` throws for 21 pairs in `9999-12-25`–`9999-12-31`.

**Why.** The old return values were not week boundaries and said so nowhere.
`MinValue.FirstOfWeek(DayOfWeek.Sunday)` returned `0001-01-01`, which is a **Monday** — a value
whose `DayOfWeek` was not the day the caller asked for. At the other end, `EndOfWeek` reported a
"week" as short as 23 hours. A caller relying on `result.DayOfWeek == firstDayOfWeek`, or on a week
being seven days long, was silently wrong. Both invariants now hold for every value these methods
return.

`OverflowException` rather than `ArgumentOutOfRangeException` because **no argument is at fault**:
the instant is valid, the `DayOfWeek` is valid, and only the result is unrepresentable. This
follows `TimeSpan.MinValue.Duration()` and `TimeSpan.MaxValue + TimeSpan.FromTicks(1)`, which throw
`OverflowException` for exactly that situation, rather than `DateTime.AddDays(value)`, which throws
`ArgumentOutOfRangeException` because a *supplied argument* pushed the result out of range.

**Before**

```csharp
var first = System.DateTime.MinValue.FirstOfWeek(System.DayOfWeek.Sunday);
// 0001-01-01 - a Monday, silently

var end = System.DateTime.MaxValue.EndOfWeek(System.DayOfWeek.Monday);
// 9999-12-31 23:59:59.9999999 - a "week" under two days long, silently
```

**After**

```csharp
try
{
    var first = System.DateTime.MinValue.FirstOfWeek(System.DayOfWeek.Sunday);
}
catch (System.OverflowException)
{
    // "The week containing 0001-01-01T00:00:00.0000000 and starting on Sunday begins
    //  before DateTime.MinValue."
}
```

If you were relying on the clamp — for example to bucket an open-ended range — clamp explicitly at
the call site, which also documents the intent:

```csharp
var first = moment < new System.DateTime(1, 1, 8)
    ? System.DateTime.MinValue
    : moment.FirstOfWeek(firstDayOfWeek);
```

**Not affected.** `0001-01-07` through `9999-12-24` inclusive — every instant in that range has
both boundaries representable for all seven alignments. Note also that each method only throws at
**its own** end of the range: `EndOfWeek` still answers for dates in year 1, and `FirstOfWeek`
still answers for dates in December 9999.

### An undefined `DayOfWeek` is rejected

**What changed.** `firstDayOfWeek` values outside `DayOfWeek.Sunday`–`DayOfWeek.Saturday` now throw
`ArgumentOutOfRangeException` with `ParamName` `"firstDayOfWeek"`.

**Why.** `(DayOfWeek)99` previously matched no day, so the walk-back loop ran until it hit year 1 —
roughly 740,000 iterations for a present-day date — and returned `0001-01-01`. Both the answer and
the cost were wrong.

Here the exception *is* `ArgumentOutOfRangeException`, because an argument genuinely is outside its
acceptable set and the caller fixes it by passing a different value. That distinction is the point:
`catch (ArgumentOutOfRangeException)` now means "my code passed something invalid" and
`catch (OverflowException)` means "my data reached the edge of representable time".

**Not affected.** Any caller passing a real `DayOfWeek`, which includes everyone using the
parameterless overloads — `CultureInfo` never supplies an undefined value.

## Deprecation timeline

| Version | State |
|---|---|
| 1.3.2 | last release with the clamping behaviour |
| 2.0.0 | clamps replaced by exceptions; `EndOfWeek` corrected near `MinValue` |

**No intervening MINOR carried a warning.** The fleet convention is to ship an `[Obsolete]` warning
in a MINOR before the MAJOR that changes behaviour, so a consumer gets a build-time notice while the
old form still works. That was not possible here: none of these changes is expressible as
`[Obsolete]` — the signatures are identical and only the returned values and thrown exceptions
differ. A consumer moving from 1.3.2 to 2.0.0 gets **no build-time notice at all**, which is why the
affected ranges are stated precisely above.

## Binary compatibility

`EnablePackageValidation` compares each build against the last published package and fails on an
incompatible change ([ADR-0004](../adr/0004-package-validation-baseline.md)). It detects **binary
and API** breaks — a removed or re-signatured member, a changed default, a nullability flip.

**Every break in this release is behavioural, so `CompatibilitySuppressions.xml` has no entry for
any of them and correctly has none.** All four public week overloads keep their exact signatures;
package validation sees an unchanged API surface and stays silent. The evidence for these changes is
in the tests that pin the new behaviour — the 21 boundary pairs and the undefined-`DayOfWeek` cases
in `DateTimeExtensionsTests`, and the property-based checks in `Tests.Fuzz` that assert each method
throws only within its own boundary window.

`AssemblyVersion` moves to `2.0.0.0` in this release and only in this release
([ADR-0001](../adr/0001-pin-assemblyversion-to-major.md)), so .NET Framework consumers need a
binding redirect crossing this boundary and not within it.
